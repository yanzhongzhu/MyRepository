## 2. 版本管理双通道总览

本系统采用 **双通道** 版本管理，互为备份，任何一条都能救人：

| 通道 | 工具 | 原理 | 适合场景 |
|------|------|------|----------|
| **① git 通道** | `manage.sh git-pull / git-rollback` | 基于 GitHub 仓库，精确到每次提交 | 版本有记录、能精确定位提交号 |
| **② 本地快照** | `manage.sh backup / rollback` | 文件级快照备份 | 出问题时兜底，无提交号也能用 |

> **原则**：发布前先 `backup` 存档；出问题先用 git 回退，git 不可靠时用本地快照回退。

## 3. manage.sh 命令速查表

在服务器任意位置执行 `bash /opt/chat-test-db/manage.sh <命令>`。

| 命令 | 作用 | 风险 |
|------|------|------|
| `current` | 查看当前版本号 + 服务状态 | 无（只读） |
| `git-log` | 查看最近提交历史（拿提交号用） | 无（只读） |
| `git-status` | 查看本地与 GitHub 的差异 | 无（只读） |
| `list` | 列出所有本地快照备份 | 无（只读） |
| `backup` | 把当前运行版本存为本地快照 | 低（只新增备份） |
| `git-pull` | 从 GitHub 拉最新代码 + 重启 | 中（会覆盖被跟踪代码文件的本地改动） |
| `rollback <标识>` | 回滚到某个本地快照 + 重启 | 中（回滚前会自动再备份当前状态） |
| `git-rollback <提交号>` | 回退 git 到指定提交 + 重启 | 中（回退前自动备份） |
| `git-rollback-last` | 回退到上一个提交 + 重启 | 中（回退前自动备份） |
| `git-sync-fix` | 强制让 GitHub 跟随本地当前版本 | **高**（`push --force`，覆盖远端历史，慎用） |

## 4. 日常发布流程（改代码 → 上线）

> **核心工作流**：本地改 → 传服务器 → 提交推送 → `git-pull` 部署

### 场景 A：修改代码后正常发布（推荐）

在 **本地** 修改代码文件（如 `app.py`、`static/index.html`）后，按此流程：

```bash
# ① 在服务器：先备份当前运行版本（保险）
bash /opt/chat-test-db/manage.sh backup

# ② 把本地改好的文件上传到服务器对应路径
#    （app.py -> /opt/chat-test-db/app.py）

# ③ 在服务器：提交并推送到 GitHub
cd /opt/chat-test-db
git add <改动文件>
git commit -m "描述本次改动"
git push origin main

# ④ 在服务器：拉取并重启生效（也可省略，因已是最新，但习惯上执行）
bash /opt/chat-test-db/manage.sh git-pull
```

### 场景 B：代码已在 GitHub，服务器一键上线

当代码改动已推送到 GitHub（无论由谁），服务器只需一条命令部署：

```bash
bash /opt/chat-test-db/manage.sh git-pull
```

该命令会自动：
1. 备份当前运行版本到 `backups/gitpull_<时间戳>/`
2. 清掉服务器本地代码文件的未提交改动（**config.json 密钥不受影响**）
3. 从 GitHub `pull --ff-only`
4. 重启服务

### 验证是否发布成功

```bash
# 检查服务状态
bash /opt/chat-test-db/manage.sh current
# 期望输出 active

# 检查运行版本（app.py 里 APP_VERSION 会暴露到接口）
curl -s http://127.0.0.1/api/info
# 期望看到 "version": "v2.0" 等字样
```

## 5. 回退 / 故障处理

### 场景 A：新版本有问题，回退到上一个版本（最常用）

```bash
# 回退到 git 上一提交
bash /opt/chat-test-db/manage.sh git-rollback-last

# 或回退到指定提交（先用 git-log 查提交号）
bash /opt/chat-test-db/manage.sh git-log
bash /opt/chat-test-db/manage.sh git-rollback 6576d31
```

### 场景 B：回退到更早的某个历史提交

```bash
bash /opt/chat-test-db/manage.sh git-log         # 找到想要版本的提交号
bash /opt/chat-test-db/manage.sh git-rollback 336c08f
```

### 场景 C：git 异常，用本地快照兜底回退

```bash
bash /opt/chat-test-db/manage.sh list            # 查看可用备份
bash /opt/chat-test-db/manage.sh rollback 20261011_222459   # 回滚到指定备份
```

> 每次 `git-rollback` / `rollback` 前，系统**都会自动把当前状态再备份一次**（`AUTO_before_rollback_*` / `gitrollback_*`），方便反悔。

### 场景 D：回退后，让 GitHub 也同步到该版本

回退后本地会领先远端，如需让 GitHub 仓库也回到该版本：

```bash
bash /opt/chat-test-db/manage.sh git-sync-fix    # ⚠️ push --force，慎用
```

## 6. 安全注意事项

### 密钥不外泄（已生效措施）

| 措施 | 状态 |
|------|------|
| `config.json` 权限 `600`（仅 root 可读写） | ✅ 已生效 |
| `config.json`、`deploy.py` 列入 `.gitignore`，不进 GitHub | ✅ 已生效 |
| 密钥不由代码硬编码，管理员网页自配 | ✅ 已生效 |
| GitHub 仓库仅含 6 个安全文件（无任何密钥） | ✅ 已核实 |

### 建议继续加固（可选）

1. **MySQL 最小权限账号**：为应用建一个只 `SELECT` 的只读账号，避免用高权限账号连库
2. **日志脱敏**：避免异常时把大模型 Key 完整打印到日志

### ⚠️ 高危操作提醒

- `git-sync-fix` 会 `push --force` **覆盖远端历史**，非必要不要用
- 不要手动修改 `config.json` 权限，保持 `600`
- 不要把 `config.json` / `deploy.py` 提交到 GitHub，`.gitignore` 已保护，请勿改动

## 7. 常见问题排查

| 现象 | 可能原因 | 处理方法 |
|------|----------|----------|
| 网页打不开 | 服务挂了 | `bash manage.sh current` 看状态；`systemctl status chat-test-db` 看日志 |
| git-pull 报错 | 本地有未提交冲突改动 | 脚本已自动 checkout/stash 处理；仍失败可 `git-status` 查看 |
| 对话查询失败 | 大模型 Key 失效 | 管理员网页用 Test 重新配置 Key |
| 连接数据库失败 | MySQL 账号/密码问题 | 检查 `config.json` 中 mysql 配置 |
| 端口占用 | 残留 gunicorn 进程 | `pkill -9 gunicorn` 后 `systemctl restart chat-test-db` |
